When a Linux server runs out of space, knowing where to look is more useful than knowing twenty directory names by heart. The same goes for finding a configuration file, figuring out where a command is installed, or understanding what survives a reboot.

The directory structure gives you clues. It separates software, configuration, persistent application data, and information about the running system. Once those differences make sense, the paths start to feel less arbitrary.

## Coming from Windows?

If you're used to drive letters, this rough translation helps. Rough is the key word: the ideas line up, the details don't.

| On Windows | On Linux |
| --- | --- |
| `C:\` | `/` |
| `C:\Users\you` | `/home/you` |
| `C:\Program Files` | `/usr` (and sometimes `/opt`) |
| Settings in the registry or `ProgramData` | `/etc` for system settings, `/var/lib` for app data |
| `%TEMP%` | `/tmp` |
| A second drive, `D:\` | A mount point, such as `/mnt/projects` |

## One tree, even when there are several disks

Linux doesn't assign a drive letter to each filesystem. Paths start at `/`, pronounced "slash" and called the root directory.

List its contents:

```sh
ls /
```

You'll see names such as `etc`, `usr`, and `var`. Your list may differ from someone else's. Distributions, installation choices, and containers all affect what appears.

The important part is that these paths belong to one directory tree. A filesystem on another disk becomes accessible through a directory in that tree. Attaching it there is called **mounting**, and the directory is its **mount point**.

For example, you might mount a second disk's filesystem at `/mnt/projects`. Its files would then be accessible through paths such as `/mnt/projects/website`. The directory name alone doesn't tell you which physical disk stores the data.

Mounting is different from copying: the files stay on that filesystem. Mounting makes them accessible at the chosen path.

The [Filesystem Hierarchy Standard](https://specifications.freedesktop.org/fhs/latest/) documents many of the conventions behind these locations. Treat it as a useful reference, with room for distribution-specific differences.

## Your home directory, the root directory, and the root user

These names are easy to mix up because "root" does several jobs.

### `/home`: personal files and settings

On a typical desktop or server, regular users have home directories under `/home`, such as `/home/dave`.

Your home holds more than documents and downloads. Many applications keep personal configuration and data there, often in names beginning with a dot. An ordinary `ls` hides those entries; `ls -a` includes them.

List the home directories, then return to your own:

```sh
ls /home
cd ~
```

The shell expands an unquoted `~` to your home directory. It doesn't mean `/home` itself, and a user's home can be configured somewhere else. Service accounts, for example, often use other locations.

### `/root`: the root user's home

The **root user** is the all-powerful admin account, with broad control over the system. Its home directory is conventionally `/root`.

That is separate from `/`, the root directory of the whole tree.

Access to `/root` is usually restricted. If your account is authorized to use `sudo`, you can list it with:

```sh
sudo ls /root
```

You don't need to run this to understand the layout. Permission denied is a useful boundary, not a reason to add `sudo` to every command.

Keep these three meanings separate:

| Name | Meaning |
| --- | --- |
| `/` | Root directory of the filesystem tree |
| `root` | Administrative user account |
| `/root` | That account's usual home directory |

## `/etc`: system configuration

The name is pronounced "et-see" by some people and "etsy" by others. Either way, if you're changing how a system service behaves, this is usually where you start.

It contains system configuration, much of it in plain text files. Personal settings usually belong in your home directory instead.

You can inspect your distribution's identification information with:

```sh
head /etc/os-release
```

Look for fields such as `NAME` and `VERSION_ID`; which fields are present depends on the distribution. This file identifies the operating system. It isn't a setting you edit to upgrade or rename the distribution.

Configuration isn't all in one giant file. A few you'll run into early:

| Path | What it holds |
| --- | --- |
| `/etc/hostname` | The machine's name |
| `/etc/passwd` | The list of user accounts (despite the name, no passwords live here) |
| `/etc/fstab` | Which filesystems get mounted at boot, tying back to the mounting idea above |
| `/etc/ssh/` | SSH client and server configuration |

Services often have their own files or directories, so when you're hunting for a setting, look for one named after the service.

Before editing, check the service's documentation. Some files are generated by another tool, and some services support small override files that are easier to maintain than changes to the main configuration. A service may also need a reload or restart before a change takes effect.

A backup helps, but knowing which file the service actually reads matters just as much.

## Where installed programs live

An application usually has several kinds of files: an executable program, supporting libraries, configuration, and data it writes while running.

Those pieces don't necessarily live together. A program might be under `/usr/bin`, read configuration from `/etc`, and store persistent data under `/var/lib`.

That separation explains much of the layout.

### Find a command before guessing its location

The video uses `which` to locate `ls`:

```sh
which ls
readlink /bin
readlink /sbin
```

`which` commonly searches the directories listed in your `PATH`, the shell's list of places to look for executable commands. Its availability and treatment of aliases vary.

For checking what your shell resolves, another useful command is:

```sh
command -v ls
```

Depending on your shell configuration, that may identify an alias or function rather than print an executable's path. That's useful information too: the name you type isn't necessarily a standalone program.

The two `readlink` commands inspect symbolic links, which are paths that point to other paths. On a merged-`/usr` installation, `/bin` and `/sbin` commonly point into `/usr`. The older paths still work.

If `readlink` prints nothing, don't assume the directory is broken. It may be an actual directory rather than a symbolic link.

### `/usr`: installed system software

Despite its spelling, `/usr` isn't where your personal documents belong, and it doesn't stand for "user" in the way you'd expect. Think of it as the main home for system software.

Explore its immediate contents:

```sh
ls /usr
```

Common subdirectories include:

| Path | Typical contents |
| --- | --- |
| `/usr/bin` | Executable commands |
| `/usr/sbin` | System administration commands, where kept separately |
| `/usr/lib` | Libraries and supporting program files |
| `/usr/share` | Architecture-independent resources, such as documentation and icons |

Library layouts vary; you may also see `lib64` or architecture-specific subdirectories.

A command being in `sbin` doesn't by itself require root access. Permissions and the operation the command performs determine that.

### `/usr/local` and `/opt`: software outside the usual package layout

`/usr/local` is traditionally reserved for software installed by the local administrator, separate from distribution-managed software:

```sh
ls /usr/local
```

For example, an administrator-maintained command might go in `/usr/local/bin`. It isn't a rule that every manually installed tool goes here: user-level installers may use locations such as `~/.local/bin`.

`/opt` is another convention you'll encounter, especially for add-on software that keeps much of its installation in a dedicated application directory:

```sh
ls /opt
```

An empty `/opt` is perfectly normal. It doesn't mean you're missing part of Linux.

### `/lib`: supporting libraries

Programs often depend on shared libraries: code that multiple programs can use without each carrying its own copy.

Traditionally, `/lib` contains libraries needed by essential programs, along with kernel modules in its hierarchy. On many modern installations it points into `/usr`:

```sh
readlink /lib
```

For troubleshooting, the practical lesson is to check your system's actual layout rather than assume that every distribution places a library at the same path.

## What changes, and what survives a reboot?

"Changes while Linux runs" is a broad category. A database should survive a reboot. A service's temporary socket usually shouldn't.

The distinction is the lifetime and purpose of the data.

### `/var`: persistent application state, logs, and caches

Start by looking at its immediate contents:

```sh
ls /var
```

Three subdirectories are especially useful:

- `/var/lib` holds persistent application state, such as database files and service-maintained data.
- `/var/cache` holds cached data applications can generally regenerate.
- `/var/log` holds many system and application logs.

You can list the log directory without opening every log:

```sh
ls /var/log
```

Not every log is a plain text file here. Some systems use a journal that you inspect with `journalctl`, and applications may send logs elsewhere.

If disk usage grows unexpectedly, `/var` is one of the first places I'd check. Start wide, then narrow down:

```sh
df -h
sudo du -sh /var/* | sort -h
```

`df -h` shows how full each mounted filesystem is and where it's mounted, so you can tell whether `/var` shares a disk with everything else or has its own. `du -sh` sizes each directory under `/var`, and `sort -h` puts the biggest at the bottom.

Finding the culprit is the easy part. "Cache" doesn't mean "delete this directory while the application is running." Use the application's cleanup tools and documentation. Deleting database files under `/var/lib` can destroy the data you're trying to preserve.

### `/tmp` and `/var/tmp`: temporary storage with different lifetimes

`/tmp` is working space for temporary files. Here's a small demonstration on a disposable practice system where `/tmp/note` doesn't already exist:

```sh
echo hi > /tmp/note
cat /tmp/note
```

The first command writes a file; the second reads it. The `>` operator overwrites an existing file at that path, which is why the filename matters.

For scripts on a shared system, use `mktemp` to create a unique temporary file instead of choosing a predictable name.

Files in `/tmp` may be removed at boot or through cleanup policies. Some systems keep this filesystem in memory.

`/var/tmp` is intended for temporary files that survive reboots, but age-based cleanup may still remove them. Neither location is a substitute for storing work you need to keep.

### `/run`: temporary state for the current boot

`/run` contains runtime information, including PID files and Unix-domain sockets. A PID file records a process identifier; a socket provides a communication endpoint.

```sh
ls /run
```

This data is cleared during boot and recreated as services start. That's why `/run` can already contain plenty of entries when you log in.

The distinction from `/var/lib` matters: a service can recreate a runtime socket, but its saved database needs to remain available after a reboot.

## `/boot`: startup files

`/boot` holds boot-related files, often including installed kernels and initial RAM filesystem images used during startup. EFI files may be on a separate filesystem mounted at `/boot/efi` or another location.

To see the kernel version currently running:

```sh
uname -r
```

This reports the running kernel, not a list of files in `/boot`. After an update, a newer kernel may be installed while the machine continues running the older one until a reboot.

That difference matters when checking whether a kernel update has actually taken effect.

## Paths that expose the running system

Not every file-like entry represents saved content on a disk.

Linux also exposes devices and kernel information through filesystem paths. You can inspect these with familiar commands, but the underlying objects behave differently from ordinary documents.

### `/dev`: interfaces to devices

`/dev` contains device files used to interact with disks, terminals, and other devices:

```sh
ls /dev
```

Some represent software devices. `/dev/null`, for example, discards data written to it. It is often used to discard unwanted command output.

A disk device entry represents access to a device; it isn't the directory where you browse that disk's documents. For that, you access its mounted filesystem.

Listing `/dev` is one thing. Writing to an unfamiliar disk device is another: it can overwrite data. You don't need to write to any device to explore this article.

### `/proc`: process and kernel information

`/proc` is a virtual filesystem: the kernel supplies the information exposed through its entries rather than storing it as ordinary disk files.

Read the uptime information:

```sh
cat /proc/uptime
```

It contains two numbers in seconds. The first is system uptime, including time spent suspended. The second represents accumulated CPU idle time; on a machine with multiple CPUs, it can exceed uptime.

You'll also see numbered directories under `/proc`. These correspond to process IDs and expose information about individual processes. `/proc/meminfo` provides system memory statistics.

This is one reason command-line tools can show so much about a running machine: many read information the kernel exposes here. Some entries also allow changing settings, so don't treat the whole directory as read-only.

### `/sys`: devices, drivers, and their relationships

`/sys` is another virtual filesystem. It exposes kernel objects and attributes, including information about devices and drivers:

```sh
ls /sys
```

Where `/proc` is useful for process and system information, `/sys` is especially useful for exploring how the kernel represents devices and their relationships.

Some attributes are writable and can affect device behavior. For this introduction, inspecting directory names is enough.

## `/mnt`, `/media`, and `/srv`: locations with conventions

These directories are easier to understand once mounting and application data make sense:

```sh
ls /mnt /media /srv
```

- `/mnt` is traditionally a mount point for a temporarily mounted filesystem. Administrators also commonly create mount points beneath it.
- `/media` is intended for removable media. Desktop tools may mount USB drives under it or use another location, such as beneath `/run/media`.
- `/srv` is intended for data provided by services on the machine. A website's content could live here, but the web server's configuration determines its actual location.

These names suggest a purpose; they don't force an application or disk to use that path. If a directory is empty or absent, check how your distribution and applications are configured.

## Use the layout to ask better questions

Imagine troubleshooting an application that won't start.

Its executable may be under `/usr`. Its system configuration may be under `/etc`. Its persistent data may be under `/var/lib`, while logs help explain the failure. A missing socket under `/run` might be a consequence of the service failing to start.

Pick a command you already use and locate it with `command -v`. Look at `/usr` and `/var`. Read `/proc/uptime` twice and notice what changes.
